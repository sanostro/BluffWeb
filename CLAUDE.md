# BluffWeb

A standalone, platform-independent PWA reimplementation of `Bluff/` (the WinForms dice bluffing game one level up) — same rules, same three languages (German/English/Dutch), built specifically for accessibility with VoiceOver (macOS/iOS Safari) and JAWS/NVDA (Windows, any browser). It does not talk to `Bluff/` at runtime; the two are parallel, independent implementations of the same game. Do not touch `Bluff/` when working here, and vice versa.

## Commands

```powershell
npm install
npm run dev       # Vite dev server
npm run build     # tsc -b && vite build
npm run preview   # serve the production build locally
```

No test runner configured. `npx tsc -b` alone typechecks without emitting (useful as a quick correctness check). A `.claude/launch.json` entry (`"bluffweb"`, at the repo root, not inside this folder) runs `npm --prefix BluffWeb run dev -- --host` for the Browser tool's `preview_start` — the `--prefix` is required because `.claude/launch.json` executes relative to the repo root, not this folder.

## Architecture

**Layering**: `src/engine/` (pure game logic — `types.ts`, `bidRules.ts`, `aiHeuristics.ts`, `aiPlayerAgent.ts`, `humanPlayerAgent.ts`, `gameEngine.ts`) → `src/i18n/` (per-language text) → `src/audio/` (Web Audio playback) → `src/names/` (AI name pool) → `src/ui/` (DOM screens) → `src/main.ts` (wiring). `src/engine/` has zero DOM/browser API dependency — it's a line-by-line port of `Bluff/Engine/*.cs` (same `BidRules.isLegalRaise`/`getSuggestedRaises` logic, same differential dice-loss rule with the exact-match exception, same `AiPlayerAgent.pickRaise` probability-weighted-random selection, same `~2.7–3.3s` AI think delay and `3s`/`6s` engine pacing). Changes to the rules almost always need to land in **both** `Bluff/Engine/*.cs` and `BluffWeb/src/engine/*.ts` to keep the two versions in sync — there's no shared code between them (see "Why no shared package" below).

**`src/i18n/language.ts`** is the TS analogue of `Bluff/Localization/ILanguage.cs`: one interface, three full implementations (`german.ts`/`english.ts`/`dutch.ts`) that were transcribed from the already-approved C# translations (`German.cs`/`English.cs`/`Dutch.cs`) for consistency, then adapted where the web UI genuinely differs (see below). `languageStore.ts` persists the choice to `localStorage` (`bluff.language`) — **unlike the WinForms version**, which asks fresh on every launch by explicit user request, the web version remembers the choice and skips straight to setup on return visits (also an explicit, separate decision — see `main.ts`'s `getStoredLanguage()` check). A "Change language" button on the setup screen re-opens the picker.

**Deliberate departures from the WinForms design** (not a 1:1 port — see the approved plan in git history / conversation for the reasoning), because web screen readers behave structurally differently from a Windows desktop app:

- **No F1–F6 shortcuts, and no dedicated "read status" buttons either.** Browsers/screen readers already claim most function keys, and a reliable cross-platform F-key hook does't exist on the web. More importantly, web screen readers browse *all* page content via their own virtual cursor, not just focusable controls (unlike Windows, where that's exactly why the WinForms version needed a real `ListBox` and on-demand query shortcuts). So instead of query shortcuts, `gameScreen.ts` renders a permanently visible, semantically labeled **status area** (`<section aria-label="…"><dl>…`) with current bid + total dice, own dice, and whose turn it is — always there to read, no action needed. This single design choice is why the UI has noticeably fewer controls than `GameForm.cs`.
- **Live announcements**: two `aria-live` regions (`polite` for most events, `assertive` for `RoundResolved`/`GameOver`) updated via `textContent`, the direct equivalent of `GameForm.Speak()`'s `RaiseAutomationNotification` call — see `speak()` in `gameScreen.ts`.
- **History log**: a plain `<ol>/<li>` list, not a `ListBox`-style control — same reasoning as the status area (virtual-cursor browsing makes a real "list of readable items" unnecessary; no `TopIndex`/`SelectedIndex` dance like `GameForm.AddHistory` needed).
- **Help screen** (`src/ui/helpScreen.ts`) is a native `<dialog>` opened with `.showModal()`, not a full-screen replacement — this matters because the `GameEngine` keeps running (its `setTimeout`-based pacing) while help is open, exactly like the WinForms `HelpForm` being modal over `GameForm` without stopping it. Don't reroute "open help" through the same screen-swap mechanism `main.ts` uses for language→setup→game, or the running game's DOM gets torn down. `renderSetupScreen` also takes an `onOpenHelp` callback and shows the same button next to its `<h1>` — instructions are reachable before a game even starts, not just mid-game.
- **Help content is one continuous document, not a chapter-by-chapter switcher**: `HelpForm.cs` pairs a `ListBox` of chapter names with a `TextBox` that gets swapped to the selected chapter's body on `SelectedIndexChanged`, because WinForms/JAWS has no cheap way to jump by heading level. The web version instead renders every chapter inline as its own `<section aria-labelledby>`/`<h2>` pair inside one scrollable `<div class="help-body" tabindex="0">` — no click-to-switch interaction at all. This isn't a simplification for its own sake: web screen readers already browse a whole page via their virtual cursor and can jump straight between `<h2>`s (VoiceOver rotor, JAWS/NVDA "H"), so a manual chapter switcher would be redundant machinery solving a problem the platform already solves better. Same reasoning as the status-area/history-log departures above. `lang.helpChaptersLabel` (the old chapter-`<nav>`'s `aria-label`) was removed when this landed — don't reintroduce it without a new use.
- **Heading-based jump navigation**: every major region in `gameScreen.ts` (status area, player overview, bid controls, game-over, history) has a real `<h2>` now, not just an `aria-label` on the `<section>` — `aria-label` alone gives no target for VoiceOver-rotor/JAWS-NVDA-"H" heading navigation, only an actual heading element does. Each section points at its heading via `aria-labelledby` instead of carrying a second, redundant `aria-label` string, so the heading text is the single source of truth for the region's accessible name. The round number stays the page's one `<h1>`; the game-over heading (`gameOverLabelEl`) doubles as the winner announcement itself, so no separate heading text was needed there.
- **Bid entry: two adjacent `<select>`s in a `<form>`, not a number input**: Anzahl was originally an `<input type="number">`; on explicit user request it's now a `<select>` just like Augenzahl already was, and both live inside one `<form>` (`bidForm`) with the Bid button as its `type="submit"`. The point is fast VoiceOver/touch swipe-navigation between two adjacent "picker" controls followed by a single confirm action, and the `<form>` groups them as one semantic unit rather than two unrelated fields. Anzahl's option range is rebuilt on every `onActionRequested` (`populateAnzahlOptions()`) up to `totalDiceInPlay() * 2` — the same ceiling `AiPlayerAgent.getAction` already uses for its own `maxAnzahl` — generous enough to cover any plausible bid without being an unbounded free-text field. Challenge stays a separate `type="button"` outside the form so it can't trigger a submit.
- **No focus movement when it becomes the human's turn**: `humanAgent.onActionRequested` deliberately does *not* call `.focus()` on any bid control anymore (it used to focus the Anzahl field). Moving focus interrupts whatever the screen reader is currently reading — in practice, the very `aria-live` announcement of the previous player's bid, which is exactly the information the user needs before acting. Focus is left wherever it already was; the live region still announces the turn change without needing focus to do it.
- **Pacing before the human's turn specifically**: `GameEngine.runRound` (`src/engine/gameEngine.ts`) awaits `ANNOUNCEMENT_PAUSE_MS` after a `BidPlaced` event *only* when the next actor's `Player.kind === "human"`. AI-to-AI turns already get natural spacing for free from `AiPlayerAgent`'s own ~3s think delay, but `HumanPlayerAgent.getAction` resolves `onActionRequested` synchronously with zero delay — without this pause, the "It's your turn" announcement landed in the same polite live region in the same tick as the just-raised bid announcement, so the screen reader only ever got to read the second one and the actual bid content was lost. This is deliberately scoped to just this one transition (not a blanket delay after every `BidPlaced`) so AI-vs-AI pacing stays unchanged.
- **Eliminated humans aren't stuck in permanent read-only spectator mode**: on `PlayerEliminated` for `HUMAN_INDEX`, `gameScreen.ts` reveals `gameOverControls` (Play again / New game) immediately — the same section and buttons the true `GameOver` screen uses — rather than waiting for the whole match (remaining AI players) to finish. Spectating still continues underneath (status/history/sounds keep updating for the AI-only rounds still in progress); the human just isn't forced to wait it out with zero available actions. If the match legitimately concludes afterward, `showGameOver` simply overwrites the same heading/section with the real winner text — no separate teardown needed. Because "Play again"/"New game" can now be clicked *before* the match engine has actually finished, both handlers set a `disposed` flag that the screen's `engine.onEvent` callback checks first and no-ops on — without it, the old, now-orphaned engine would keep running in the background (it's never explicitly cancelled, `GameEngine` has no abort mechanism) and its sound effects for the remaining AI-vs-AI rounds would keep firing audibly underneath the brand new game the user just started.
- **`names.txt` → `localStorage`**: no filesystem next to a `.exe` on the web, so `src/names/aiNames.ts` starts from the same default name list and lets the user edit it via a `<textarea>` on the setup screen (`bluff.aiNames` in `localStorage`) instead of an external file.
- **Sound/panning is simpler here than the WinForms port**, not harder: `src/audio/audioEngine.ts` uses `AudioContext` + `StereoPannerNode`, which genuinely support concurrent independently-panned playback natively — none of `Bluff/Sounds/AudioEngine.cs`'s dedicated-Dispatcher-thread workaround is needed (that workaround existed specifically because `System.Media.SoundPlayer` can only play one sound at a time; the browser has no such limitation). `AudioContext` must be `.resume()`d from within a real user gesture (browser autoplay policy) — `audioEngine.unlock()` is called from both the language-select "Continue" button and the setup screen's "Start" button (the latter as a fallback for returning visitors who skip the language screen entirely via the stored-language path).

**Pitfall already hit once**: the status area's `<dl>` built its "current bid" `<dt>` by string-splitting a full sentence (`currentBidLabelNone.split(":")[0]`), while the paired `<dd>` held a *different* full sentence that repeated the same lead-in text (`"Current bid: 5 × 3 with 15 dice in play"`) — a screen reader walking the `<dl>` heard "Current bid" / "Current bid: 5 × 3…" back to back. Fixed by giving the `<dt>` its own short dedicated string (`currentBidLabel`) and trimming the `<dd>` string (`currentBidWithTotal`) down to just the value, no repeated lead-in — the general rule this leaves behind: a `<dt>`/`<dd>` pair's value text should never re-state the label the `<dt>` already provides.

**Pitfall already hit once**: `Language.defaultPlayerNameFallback` is stored as the actual `Player.name` when the name field is left blank — it must be a plain noun ("Player"/"Spieler"/"Speler"), not a pronoun like "You"/"Sie". A pronoun there breaks third-person event narration (discovered live: "The bid was correct. You gives up one die." instead of "...Player gives up..."). The status area's "Turn: You" display is unaffected since that's wired separately (`yourTurnValue`/`playerTurnValue` in `gameScreen.ts` special-case `currentPlayerIndex === HUMAN_INDEX` rather than relying on the stored name) — don't reintroduce a pronoun into the fallback name itself.

**Why no shared package between `Bluff/` and `BluffWeb/`**: the approved plan calls for these to stay independent (different languages entirely — C# vs. TypeScript — so there's nothing to literally share); `src/engine/` is deliberately DOM-free specifically so it could run unmodified on a future multiplayer server (see below), not so it could be imported by the C# project.

## Multiplayer (not implemented — advisory only)

`src/engine/` was deliberately kept DOM-free so it could run as-is inside a Node process. If cross-device multiplayer is ever built: an authoritative WebSocket server reusing this same `engine/` code is the recommended direction over WebRTC/peer-to-peer, specifically *because* this is a bluffing game — a peer that can inspect or fake its own "hidden" dice has an obvious incentive to cheat, so a server that owns the real game state (the way `GameEngine` already does locally) matters more here than in most turn-based games. See the conversation/plan history for the fuller comparison (WebSocket server vs. WebRTC+PeerJS vs. backend-as-a-service vs. simple polling).

## Verification

No live JAWS/NVDA/VoiceOver access in this environment — structure was checked via the Browser tool's `read_page` (confirms real `radiogroup`/`listbox`/`table`/`region`/`status` semantics render correctly, not just visually) and a full manual play-through (language pick → setup → several rounds of bids → a challenge → resolution text/sounds), not by an actual screen reader. Treat that as a strong structural signal, not a substitute for a real VoiceOver/JAWS/NVDA pass before considering this "done" the way `Bluff/` is.
